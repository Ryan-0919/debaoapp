# 批改分发与套卷流程

## 目标

批改业务分为用户端、运营后台和兼职批改工作台三类角色。用户先选择可批改套卷，再逐题作答并提交；服务端完成 AI 首轮建议后进入人工队列；管理员可以按科目权限把任务分发或改派给兼职老师；人工完成后由管理员发布报告，用户只能查看自己已发布的报告。

## 用户端流程

1. `批改服务`读取 `GET /v1/grading/papers`，展示已发布套卷和批改次数。
2. 点击套卷进入 `GradingPaperDetail`，读取 `GET /v1/grading/papers/:id`，显示题目列表、总分和建议用时。
3. 点击单题进入 `SubjectiveAnswer`，使用 `gradingPaperId` 和 `gradingQuestionId` 加载服务端案情、小问和分值。作答页右上角保留法条检索入口。
4. 提交时携带 `paperId`、`questionId`、小问答案和 `Idempotency-Key`。每道题独立扣除一次批改次数，重复请求返回同一任务。
5. `批改服务`历史记录展示状态、套卷、题目、分数和老师评语。已发布记录进入 `GradingReport`，读取 `GET /v1/grading/submissions/:id/report`。

## 后台分发

- `GET /v1/admin/grader-accounts`：读取启用中的兼职老师，只返回账号、显示名和科目权限，不返回密码哈希、AI 配置或成本数据。
- `POST /v1/admin/grading/:id/assign`：管理员首次分发。请求体：`graderId`、可选 `dueAt`、`reason`。
- `POST /v1/admin/grading/:id/reassign`：管理员改派。旧的 `available/claimed` assignment 标记为 `cancelled`，新 assignment 记录新的老师和截止时间，旧记录和操作原因保留在审计事件中。

分发前必须满足：任务状态为 `manual_queued`、`manual_claimed`、`manual_returned` 或 `manual_expired`；老师账号启用；老师拥有该题科目权限；截止时间晚于当前时间；分发原因不少于 2 个字符。分发后的任务状态为 `manual_claimed`，兼职老师只能在自己的工作台看到该任务。

## 演示数据

开发环境预置两套套卷、三道题、四条用户批改任务、三名兼职老师账号和多种状态：等待人工、人工批改中、已发布、AI 异常。账号仅用于本地演示：

- `grader / change-me-grader`：民法
- `grader-criminal / change-me-criminal`：刑法
- `grader-all / change-me-all`：全科

真实环境必须关闭本地密码分支，改用独立身份源和安全密码存储。

## 关键安全约束

- OpenAI key、模型、prompt、token 和成本只在服务端，不能返回兼职工作台。
- 用户接口按当前用户过滤提交和报告，不能通过修改任务 ID 读取他人数据。
- 分发、改派、领取、退回、评分、发布均写入 `grading_events` 和管理员审计日志。
- AI 只提供结构化建议，人工老师和管理员才决定最终分数。
# 2026-08-31 提交成功页与演示任务补充

- 用户提交套卷内单题后进入独立成功页，展示提交编号、预计反馈时间和四阶段批改进度。
- 成功页提供“查看批改记录”“返回套卷”“返回首页”入口。
- 批改老师工作台在开发环境固定补充待领取、批改中、已提交、已退回演示数据。
- 待领取任务按老师授权科目过滤，列表展示套卷、题目、AI 建议分和截止时间。
- 老师领取任务后按 AI 建议预填采分点分数，人工可修改并填写总评、建议及差异原因。
- 人工提交后任务进入“等待主管复核发布”，只有主管发布后用户才能查看正式报告。

# 行内批注与采分点复核

## 批改老师抽屉

批改老师继续在抽屉中完成任务，抽屉宽屏为左右双栏，窄屏自动纵向排列：

- 左栏展示案情、批改依据和每个小问的用户答案。鼠标选中文字后可以直接点击“划线”，也可以添加“正确 / 加分”“错误”“重点”或“点评”标记；划线会叠加在原句下方，点评标记必须填写文字。
- 彩色标记点击后显示引用原文、老师点评和删除操作；“撤销最近批注”只撤销当前编辑会话的最后一条标记。选区不能与已有标记重叠，避免报告区间歧义。
- 右栏展示 AI 首轮建议作为参考，并填写本题人工总分、老师总评和改进建议。老师不在此处逐项打分，批改依据是左栏用户答案原文上的划线、错误标记和点评。
- 点击提交时服务端重新校验小问、批注区间、引用文本、人工总分和评语，防止只改前端数据。批注随人工复核一起保存；采分点仍保留在题目配置和报告数据中，用于解释批改依据，不作为老师的操作表单。

## 数据与接口

`GradingReview` 和 `GradingReport` 包含：

- `answerAnnotations`：`id`、`subQuestionId`、`start`、`end`、`quote`、`type`、`comment`、`scoreDelta`。
- `pointResults[].status`：`hit`、`partial`、`missed`，并保留人工分数、点评和证据。
- `missedPointIds`：由服务端根据采分点状态生成，不能由客户端伪造。
- `GradingReport.answers`：发布时保存答案快照，确保以后题目版本变化仍能还原报告中的原文。

## 原文批注分值标识

- “正确”批注只在答案原文上显示蓝色对勾，不展示分值。
- “加分”批注保存正数 `scoreDelta`，在原文上方显示 `+N`。
- “错误”批注保存负数 `scoreDelta`，使用红色错误线并在原文上方显示 `-N`；分值由批改老师在工具栏输入。
- “错误”批注必须同时填写点评内容；使用红色波浪线标注原句并在原文上方显示 `-N`。
- 用户点击红色错误标注后，展示原句、扣分数值和老师点评；报告下方同时保留可点击的点评列表。
- 独立“点评”使用红色波浪线标注原句，点评文字在批注详情中展示。
- 用户端报告与批改工作台使用相同的批注类型和分值数据，避免出现后台与用户端含义不一致。

数据库迁移文件为 `debao-server/migrations/020_grading_annotations.sql`。发布报告后，用户端 `GradingReport` 展示答案原文批注、点击点评、采分点状态和独立的遗漏采分点清单。
